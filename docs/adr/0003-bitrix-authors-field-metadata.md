# 3. Метаданные полей: автор — Bitrix, виджет — read-only зеркало

Дата: 2026-07-03
Статус: Принято

## Контекст

Поля смарт-процесса «договор» и товаров каталога меняются бизнесом напрямую в Bitrix
без участия разработчика виджета. Текущая реализация зашивает коды полей в код
(`ufCrm7_<timestamp>` в мапперах, ID товаров каталога в `productRecords`), из-за чего
любое изменение полей в Bitrix ломает виджет, а перенос на другой портал невозможен —
коды UF-полей содержат timestamps создания и уникальны для каждого портала.

Решено перейти на метаданные полей (см. `field metadata` в [CONTEXT.md](../../CONTEXT.md)):
формы и хранение подстраиваются под актуальный набор полей динамически, по образцу
метаданных Twenty. Возник вопрос, кто владеет метаданными:

- **A. Bitrix — автор, виджет — зеркало (read-only).** Виджет тянет описания полей из
  Bitrix, хранит per-portal кэш и рендерит по нему. Полей в Bitrix не создаёт.
- **B. Виджет — автор (модель Twenty).** Поля создаются в виджете и уходят в Bitrix;
  бизнес перестаёт править поля в Bitrix напрямую.
- **C. Двунаправленно.** Создавать можно и там и там, виджет мёржит.

## Решение

Вариант **A**: Bitrix — единственный автор метаданных полей, виджет — read-only зеркало.

Обоснование:

- Исходная боль — «разработчик не контролирует решения бизнеса, поля меняются без него».
  Это констатация: автором был и останется Bitrix. Вариант B требует организационной
  дисциплины («поля правим только в виджете»), которой заведомо нет.
- Вариант C покупает малую выгоду ценой двустороннего мёржа определений полей —
  худший класс сложности в синхронизации.
- Консистентность с ADR-0002: Bitrix — источник правды и для данных, и для формы данных.

Следствие: «метаданные» здесь — не собственная модель (как в Twenty), а кэш чужих
определений. Конфликтов записи метаданных не существует по построению; единственный
режим сбоя — устаревание зеркала, которое устраняется очередным обновлением из Bitrix.

## Последствия

**Плюсы:**
- Синхронизация метаданных однонаправленная — не нужен мёрж и разрешение конфликтов.
- Виджет переносим между порталами: коды полей не зашиты, а читаются из портала.
- Бизнес продолжает работать в Bitrix как привык — никакого организационного перехода.

**Минусы / на что обратить внимание:**
- Виджет всегда догоняет: между изменением поля в Bitrix и обновлением зеркала формы
  могут рендериться по устаревшей схеме.
- Служебные поля, нужные самому виджету, нельзя «завести» через метаданные — им нужен
  отдельный механизм вне этой модели (если вообще понадобятся).

## Почему это записано

Будущий разработчик, знакомый с Twenty, ожидает, что приложение владеет метаданными и
управляет схемой. Здесь сознательно наоборот, и попытка «дореализовать» создание полей
из виджета (вариант B/C) сломает главное упрощение — отсутствие конфликтов записи.
