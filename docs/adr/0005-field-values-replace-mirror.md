# 5. Значения динамических полей — replace-зеркало ответа Bitrix, без мержа

Дата: 2026-07-03
Статус: Принято

## Контекст

С переходом на динамические поля (ADR-0003, ADR-0004) значения полей договора и модуля
хранятся в JSONB-колонке `values`. Схему этих полей контролирует бизнес в Bitrix:
поля появляются, удаляются, меняют тип — без уведомления виджета (событий об изменении
определений полей у смарт-процессов в Bitrix нет). Нужна политика: что такое `values`
по отношению к Bitrix и что происходит при записи и при эволюции схемы.

Варианты:

- **A. Replace-зеркало.** `values` всегда равно последнему полному ответу Bitrix по
  элементу. Любой путь записи (вебхук, sync, создание/правка из виджета) завершается
  полной перезаписью `values` из ответа Bitrix.
- **B. Мержимое состояние.** Точечные обновления ключей + процедуры чистки ключей-сирот
  при обновлении зеркала метаданных.

## Решение

Вариант **A**. Инварианты:

- запись из виджета — Bitrix-first (как в ADR-0002): `crm.item.add`/`update` → ответ
  Bitrix содержит полный элемент → `values` перезаписывается **из ответа**, не из формы;
- вебхук/sync → перечитанный элемент → полная перезапись;
- удаление поля в Bitrix не требует чистки: ключ-сирота исчезает при следующем
  обновлении элемента, до того безвреден (UI рендерит только поля из метаданных);
- смена типа поля не требует миграции значений: рендер по текущим метаданным,
  значение обновится в новом формате при следующем обновлении элемента.

## Последствия

**Плюсы:**
- Нет конфликтов, дрейфа и процедур чистки — рассинхрон самоустраняется следующим
  обновлением, консистентно с ADR-0002 («рассинхрон — отложенная работа»).
- Эволюция схемы полей (добавление/удаление/смена типа) не порождает миграций данных.

**Минусы / на что обратить внимание:**
- После записи из виджета в БД лежит то, что Bitrix *принял*, а не то, что пользователь
  ввёл: если форма была отрисована по устаревшим метаданным и Bitrix молча проигнорировал
  поле — пользователь увидит реальность Bitrix. Это считается честностью зеркала,
  а не багом.

## Почему это записано

Разработчик, увидев «пользовательский ввод не сохранился в БД как есть», решит, что
забыли записать данные формы, и добавит запись из формы в обход ответа Bitrix. Это
создаст дрейф между БД и Bitrix и вернёт весь класс проблем мержа, от которого это
решение избавляет.
