# 4. Вид модуля — данные, а не схема: одна таблица module с JSONB-значениями

Дата: 2026-07-03
Статус: Принято

## Контекст

Виды модулей зашиты в схему и код: пять таблиц (`vats`, `chat_bot`, `voice_robot`,
`webform`, `autoinformation_module`) с типизированными видоспецифичными колонками
(`lines_count`, `additional_users`, `duration`, …), junction-таблицы
(`chat_bot_messengers`, `webform_webform_type`), `ProductEnum`, зашитые ID товаров
каталога в `productRecords` (iblock 15, ID 4930/4973/…), тройной диспатч по виду
в `productFuncs.ts`, отдельные API-роуты и ветки модалок на каждый вид.

Бизнес меняет каталог товаров в Bitrix без участия разработчика: новый вид товара
означал новую таблицу + мапперы + роуты + модалку; смена ID в каталоге молча ломала
определение типа. Та же боль, что с полями договора (см. ADR-0003).

Варианты:

- **A. Полный коллапс:** одна таблица `module`; вид = данные (ссылка на родительский
  товар каталога); видоспецифичные поля — в JSONB по [[field metadata]].
- **B. Гибрид:** пять таблиц остаются, динамика только для «дополнительных» полей.
- **C. Динамика только для договора,** товары как есть.

Для хранения динамических значений рассматривались: JSONB-колонка, EAV-таблица,
динамический DDL (модель Twenty — реальные колонки на каждое поле).

## Решение

Вариант **A**. Одна таблица `module`:

- системные колонки — только то, на что опирается сам виджет: идентичность
  (`id`, `bitrix_id`, `portal_id`, уникальность `(portal_id, bitrix_id)`), связи
  (`contract_id`, `tariff_id` — настоящие FK), вид (`parent_product_id`) и встроенные
  поля product row Bitrix (`price`, `quantity`, `active`, `title`) — их схема стабильна
  на стороне Bitrix;
- всё видоспецифичное — в JSONB-колонке `values`; какие это поля и как их рендерить,
  описывает зеркало метаданных (ADR-0003). Множественные свойства — массивы в JSONB,
  junction-таблицы не нужны.

Аналогично договор: остаётся отдельной таблицей (identity + FK `company_id` + `name`
+ `values` JSONB); справочные таблицы `contract_status`/`contract_doc_type`/
`contract_prolongation`/`contract_original_type` упраздняются — варианты списочных
полей живут в метаданных поля.

Хранение — **JSONB, не EAV и не динамический DDL**:

- EAV даёт худшие запросы и ту же нетипизированность без выгод;
- динамический DDL (как в Twenty) конфликтует с ADR-0001 (структура БД меняется руками
  в SQL, `prisma db pull`) — автоматическое порождение колонок сделало бы схему
  неуправляемой, а Prisma-клиент всё равно не знает про рантайм-колонки;
- универсальной таблицы «record» на все сущности (полная модель Twenty) не делаем:
  динамических сущностей ровно две (договор, модуль), их состав фиксирован,
  связи между ними — настоящие FK.

## Последствия

**Плюсы:**
- Новый вид товара в каталоге = ноль правок кода и схемы.
- Умирают: пять таблиц модулей, junction-таблицы, `ProductEnum` как ось,
  `productRecords`, диспатч-словари `productFuncs.ts`, пять комплектов роутов/мапперов.
- Один рендерер форм и один комплект API на все виды.

**Минусы / на что обратить внимание:**
- Видоспецифичные поля теряют compile-time типизацию: валидация — в рантайме
  по метаданным.
- Фильтры по видоспецифичным полям — JSONB-запросы (индексы GIN при необходимости),
  без FK-целостности.
- Логика, зависящая от конкретного поля по имени (расчёты, фильтры виджета по статусу
  договора), требует механизма «ролей полей» — имя поля контролирует бизнес.
  На момент решения вычислений на видоспецифичных полях в коде нет; механизм ролей —
  отдельное решение.

## Почему это записано

Схлопывание типизированных таблиц в JSONB выглядит как «потеря нормальности» БД, и
будущий разработчик может захотеть «вернуть нормальные колонки» для нового вида модуля.
Это вернёт исходную боль: схему полей контролирует бизнес в Bitrix, код догонять не
обязан. Обратное решение (типизировать поле) допустимо только повышением его до
системной колонки с записью, зачем.
