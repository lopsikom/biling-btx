# 1. БД — source of truth, схема Prisma через `db pull` (без `prisma migrate`)

Дата: 2026-06-18
Статус: Принято

## Контекст

Проект использует Prisma 7 поверх Postgres. У Prisma два рабочих процесса для схемы:

- **migrate-first** (по умолчанию): `schema.prisma` — источник правды, изменения
  применяются к БД через `prisma migrate`;
- **introspect-first**: источник правды — сама БД, а `schema.prisma` подтягивается
  из неё через `prisma db pull`.

Структура БД этого проекта развивается отдельно (правки SQL делаются прямо в Postgres).
В схеме уже зафиксированы артефакты этого: snake_case-имена и опечатки из самой базы
(`tarrif_id`, `last_activty_by`), которые нельзя «исправить» в Prisma, не сломав соответствие
реальным колонкам.

## Решение

Источник правды для структуры БД — **сама БД**, а не `schema.prisma`.

- Изменения схемы делаются в Postgres (SQL вручную), затем подтягиваются:
  `npm run updateDB` (= `prisma db pull && prisma generate`).
- `schema.prisma` и сгенерированный клиент (`server/services/models/generated/prisma/**`)
  **не редактируются руками** — перегенерируются командой выше.
- `prisma migrate` **не используется**.

## Последствия

**Плюсы:**
- Нет рассинхрона между миграциями Prisma и реальной структурой БД.
- Опечатки/имена из БД отражаются один-в-один — код всегда соответствует колонкам.

**Минусы / на что обратить внимание:**
- Нельзя положиться на `prisma migrate` для версионирования схемы — история изменений
  БД живёт вне Prisma.
- Соблазн «починить» `schema.prisma` или опечатку (`tarrif_id`) ломает соответствие БД —
  делать этого нельзя.
- Перед работой со схемой нужен доступ к актуальной БД, чтобы `db pull` дал верный результат.

## Почему это записано

Без контекста новый разработчик (или агент) увидит `schema.prisma` и опечатки в именах
и решит, что схема — источник правды, который надо привести в порядок через `prisma migrate`.
Это сломает рабочий процесс. ADR существует, чтобы это решение не переоткрывалось.
