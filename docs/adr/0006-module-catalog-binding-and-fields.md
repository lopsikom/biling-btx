# 6. Виды модулей — явный список товаров; поля — свойства offer'а по образцу

Дата: 2026-07-06
Статус: Принято

## Контекст

Этап 2 рефактора (модули, см. ADR-0004) требует зеркала метаданных для каталога —
аналога `field metadata` договора. Разведка живого каталога портала (read-only зонд
по `catalog.product.list` / `catalog.productProperty.list` / `catalog.product.offer.list`)
вскрыла две особенности, которых нет у договора:

1. **Виды модулей разбросаны по разным подразделам** каталога вперемешку с легаси
   (голосовой робот — раздел 38, ВАТС — 41, обзвон — 39, …; плюс десятки нерелевантных
   товаров в разделе 45). Привязка к одному разделу (как предполагалось в ADR-0003)
   не отделяет биллинговые товары от прочих.

2. **Свойства offer'ов заведены на весь каталог (iblock 16) сразу**, а не на конкретный
   товар. `catalog.productProperty.list` отдаёт единый плоский список из ~15 свойств
   (`property308`…`property322`), и Bitrix **не хранит связь «свойство↔вид»**. У образца
   offer'а каждого вида заполнены только свои свойства (у «Обзвона» — «Тариф АИ» и
   «Канал связи», у «Веб-формы» — «Тариф веб-формы»), остальные `null`.

## Решение

**Виды модулей — явный список parentId** в [[portal binding]] (`module_product_ids`),
а не раздел каталога. Админ отмечает конкретные товары как биллинговые модули.
Отсекает легаси, не зависит от структуры разделов (которую бизнес может перекроить).

**Поля модуля — два рода:**
- *системные* (вшиты в код, одинаковы у всех видов): `price`, `quantity`, `active`,
  `title`, связь с договором — это встроенные поля product row Bitrix;
- *динамические* (метаданные каталога): свойства offer'а. Набор полей вида **выводится
  по образцовому offer'у** — свойство релевантно виду, если у образца этого вида оно
  непустое. Это единственный способ не показывать мусорные поля, раз Bitrix связь не
  хранит; согласуется с «семантически слепым» виджетом (ADR-0003): знание берётся из
  данных, а не зашивается.

Значения свойств хранятся в `module.field_values` (replace-зеркало, ADR-0005);
offer'ы приносят человекочитаемые значения списков (`valueEnum`), так что отдельный
запрос вариантов для отображения не нужен.

## Последствия

**Плюсы:**
- Список видов явный и точный — ноль легаси-мусора, независимость от разделов.
- Форма вида показывает только релевантные поля, без зашитого знания о видах.
- Умирают зашитые `productRecords`/`property3XX`-мапперы (`bitrixProductProps.ts`).

**Минусы / на что обратить внимание:**
- Эвристика «непустое у образца → релевантно» требует хотя бы одного заполненного
  offer'а-образца на вид; у вида без образца поля не выведутся (деградация до системных).
- Свойство, у вида опциональное и в образце пустое, не покажется — приемлемо, т.к.
  бизнес заполняет образцы репрезентативно.
- Связанные услуги бизнес может выделять в *отдельные* виды-товары (ВАТС и «ВАТС
  хранение записей» — parentId 4973/4975), а не в свойства одного. UI и эвристика не
  должны предполагать взаимоисключающие виды или один модуль на «функцию» договора.

## Почему это записано

Разработчик по аналогии с договором ожидает, что Bitrix отдаёт поля конкретного товара
(как `crm.item.fields` — поля конкретного смарт-процесса). Здесь это не так: список
свойств общий на каталог, связь с видом выводится эвристикой. Попытка «спросить поля
товара напрямую» упрётся в то, что такого API нет, и вернёт к зашитому знанию о видах.
